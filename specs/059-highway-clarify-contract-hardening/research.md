# Research: Highway Clarify Contract Hardening

**Feature**: 059-highway-clarify-contract-hardening

## Decision: Preserve Feature 058 as the baseline and make additive contract corrections

**Rationale**: The requested behavior strengthens metadata, output contracts, deterministic processing, privacy handling, and regeneration without changing supported source families, advisory semantics, or source ownership. Keeping the baseline intact minimizes migration risk.

**Alternatives considered**: Replacing Feature 058 with a new implementation would obscure compatibility and broaden the change unnecessarily.

## Decision: Use `CLAR-<ARTIFACT-ID>` as the sole stable clarification identifier

**Rationale**: The identifier is directly derived from the already validated exact uppercase source identifier, requires no new allocation state, and remains stable across regeneration.

**Alternatives considered**: A generated UUID or path-derived identifier would introduce nondeterminism or duplicate identity sources.

## Decision: Resolve profiles by explicit precedence and continue when no profile resolves

**Rationale**: Artifact-local rules are closest to the source, artifact-type defaults provide shared policy, and the global profile provides a final repository default. Missing optional policy must not make clarification unavailable.

**Alternatives considered**: Merging all profiles would create precedence conflicts; requiring a profile would make existing artifacts fail unexpectedly.

## Decision: Make privacy filtering cover every retained clarification value

**Rationale**: Findings, copied evidence, responses, history, and metadata can each retain sensitive data. Filtering only source text would leave later user-supplied responses or copied evidence as an exposure path.

**Alternatives considered**: Trusting responses or limiting filtering to credentials would leave regulated personal data and secondary records unprotected.

## Decision: Define canonical deterministic ordering and serialization

**Rationale**: Category order alone does not fully stabilize output. Within-category ordering by source position, field name, and finding identifier provides a total order. Generated bytes must use the template's fixed section order, normalized line endings, and no volatile metadata in the compared output.

**Alternatives considered**: Filesystem order, timestamps, recency, or model-produced order are not reproducible guarantees.

## Decision: Regeneration reconciles current findings with retained valid state

**Rationale**: Generate must recalculate current evidence while retaining responses and history only when their finding identity/evidence remains valid. Stale responses must not migrate to unrelated findings.

**Alternatives considered**: Replacing the entire record would lose audit state; never recalculating would leave findings stale.

## Decision: Conflict and privacy failures are no-write failures

**Rationale**: Revision validation and redaction are safety boundaries. A failed check must leave artifact bytes, revision, and history unchanged.

**Alternatives considered**: Partial writes or best-effort redaction would make retained governance state difficult to trust.

## Decision: The shared clarification template owns the complete generated structure

**Rationale**: One authoritative template prevents drift between skill instructions, generated records, and validation. The template will include explicit counts and standardized status fields.

**Alternatives considered**: Duplicating structure in the skill would create two contracts that can diverge.

## Decision: Validate with existing Bash 3.2-compatible repository checks and focused probes

**Rationale**: The repository already validates skills, libraries, generated correspondence, packaging, and seeded artifact-class failures. Extending those surfaces is more consistent than adding a new runtime or test framework.

**Alternatives considered**: A new dependency or service would violate the repository's dependency and portability constraints.
