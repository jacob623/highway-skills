# Feature Specification: Capability Catalog

**Feature Branch**: `184-capability-catalog`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "Create a repository-wide Capability Catalog generated from accepted Reference Implementations, with CAP###### index identifiers, business-readable capability titles, realization providers, deterministic ordering, and atomic publication with the owning implementation."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Publish capabilities from implementation evidence (Priority: P1)

As a repository owner, I want accepted Reference Implementations to expose the business capabilities they realize so that the technology landscape can be understood through implementation knowledge.

**Why this priority**: The catalog has value only when it is derived from authoritative implementation evidence and gives business stakeholders a direct view of realized outcomes.

**Independent Test**: Provide accepted Reference Implementations with one or more business capabilities and realization values, run implementation publication, and verify the implementation record remains authoritative while the catalog contains the corresponding rows.

**Acceptance Scenarios**:

1. **Given** an accepted Reference Implementation realizes E-Commerce through Shopify and Digital Downloads through Shopify, **when** it is published, **then** the catalog contains one row for each capability with the same RI parent and realization value.
2. **Given** a capability is realized by Shopify and Amazon, **when** the implementation is published, **then** the catalog represents both realization values without creating duplicate capability identities or separate capability records.
3. **Given** a Reference Implementation contains no supported business capability evidence, **when** publication runs, **then** no capability row is invented and the implementation workflow reports the absence according to its existing evidence rules.

### User Story 2 - Navigate business capabilities and their providers (Priority: P1)

As a business or technology stakeholder, I want one repository-wide index of capabilities, owning implementations, and realization providers so that I can identify what the organization can do, how it is realized, and where providers are duplicated.

**Why this priority**: Direct business-to-technology navigation is the primary user value of the catalog.

**Independent Test**: Seed multiple accepted implementations with overlapping capability titles and providers, load the catalog, and verify that each row identifies exactly one RI parent and at least one realization value, while repeated providers remain visible across capabilities.

**Acceptance Scenarios**:

1. **Given** several implementations realize Registration, Family Communications, and Customer Synchronization, **when** a stakeholder reads the catalog, **then** each row shows a business-readable title, its RI parent, and its provider or realization mechanism.
2. **Given** Shopify realizes capabilities under multiple Reference Implementations, **when** the catalog is reviewed, **then** Shopify appears in each applicable row and can be identified as a repeated provider without a separate technology inventory.
3. **Given** an assessment finding names a capability or provider relationship, **when** assessment context is used, **then** the catalog provides the direct RI and provider references needed to locate the affected implementation evidence.

### User Story 3 - Preserve deterministic and authoritative publication (Priority: P1)

As a repository maintainer, I want catalog generation to be repeatable and failure-safe so that derived capability navigation never becomes more authoritative than the Reference Implementation that produced it.

**Why this priority**: A generated index must not create partial, orphaned, or nondeterministic repository state.

**Independent Test**: Run equivalent implementation inputs repeatedly and exercise missing, malformed, duplicate, validation-failure, and write-failure fixtures; compare generated bytes and all pre-operation bytes.

**Acceptance Scenarios**:

1. **Given** identical accepted Reference Implementations and catalog state, **when** generation runs repeatedly, **then** capability rows, identifiers, ordering, version, and Next ID are identical.
2. **Given** a capability row would lack an RI parent or a realization value, **when** validation runs, **then** publication fails without changing the implementation record or catalog.
3. **Given** a record write succeeds but catalog publication fails, **when** the operation ends, **then** neither the new implementation publication nor the capability catalog change remains.
4. **Given** a capability is removed or changed in its owning Reference Implementation, **when** the catalog is regenerated, **then** the derived row set reflects the accepted implementation evidence and no orphaned capability row remains.

## Edge Cases

- A Reference Implementation is missing, malformed, duplicated, unreadable, or not accepted; it cannot produce catalog entries and publication follows the existing implementation failure behavior.
- Capability evidence uses an implementation component, platform component, queue, gateway, or database name rather than a business outcome; it is rejected or remains unresolved rather than being recorded as a capability.
- One capability has multiple realization values; each value is represented without creating multiple independent capability artifacts.
- Two capabilities under one RI have the same title; validation rejects the ambiguous duplicate or applies the owning implementation contract without silently merging them.
- Multiple Reference Implementations use the same capability title; each remains a separately parented catalog row.
- The catalog contains duplicate CAP identifiers, an invalid Next ID, an orphaned Parent, a missing Realized By value, malformed rows, or an ordering violation; publication fails without partial writes.
- No accepted Reference Implementations exist; the catalog remains valid with no capability entries and the next identifier unchanged.
- Assessment findings refer to a capability or provider that no longer appears in regenerated implementation evidence; the catalog does not preserve a stale row as authoritative evidence.
- A generated output would contain timestamps, filesystem order, environment state, randomness, or session identifiers; those values are excluded.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The implementation workflow MUST derive the Capability Catalog only from accepted Reference Implementation evidence.
- **FR-002**: Reference Implementations MUST remain authoritative for capability meaning, evidence, ownership, and lifecycle; the catalog MUST be a generated projection.
- **FR-003**: The Capability Catalog MUST be persisted at `implementations/capabilities.md`.
- **FR-004**: The catalog MUST contain exactly the fields `ID`, `Parent`, `Title`, and `Realized By` for each capability index row, in addition to its Version, Next ID, and index heading.
- **FR-005**: Each catalog identifier MUST use the `CAP######` format and MUST be unique within the catalog.
- **FR-006**: A capability row MUST reference exactly one owning `RI######` Parent.
- **FR-007**: A capability row MUST contain at least one non-empty Realized By value identifying a provider, platform, product, technology, service, process, or other realization mechanism.
- **FR-008**: Capability Titles MUST describe business-recognizable outcomes and MUST NOT merely name implementation components such as databases, queues, gateways, or event processors.
- **FR-009**: Multiple Realized By values MUST be supported for one capability without creating a separate capability artifact for each value.
- **FR-010**: Multiple Reference Implementations MAY realize the same capability title, and the catalog MUST preserve each parent relationship.
- **FR-011**: No standalone capability record files, `CAP######.md` files, capability workflow, or independent capability acceptance boundary MUST be created.
- **FR-012**: Capability identifiers MUST exist only in the catalog and MUST NOT be treated as authoritative artifact identifiers.
- **FR-013**: The implementation workflow MUST allocate capability identifiers deterministically and MUST advance Next ID exactly once for each newly allocated catalog identifier.
- **FR-014**: Existing capability identity and identifier assignments MUST remain stable when unrelated capabilities are added, removed, or reordered.
- **FR-015**: Catalog rows MUST be ordered by Parent RI identifier, then Capability Title, then Capability identifier.
- **FR-016**: Identical accepted implementation inputs and prior catalog state MUST produce byte-identical catalog content, identifiers, version behavior, and row ordering.
- **FR-017**: Catalog generation MUST exclude timestamps, creation dates, modification dates, filesystem order, environment metadata, random values, and session identifiers.
- **FR-018**: The implementation workflow MUST validate that every row has exactly one valid RI parent, at least one Realized By value, a business-outcome title, a unique CAP identifier, and valid ordering before publication.
- **FR-019**: A missing, unreadable, malformed, duplicated, ambiguous, or non-accepted Reference Implementation MUST NOT create a catalog row.
- **FR-020**: A validation, allocation, implementation-write, or catalog-write failure MUST preserve all pre-operation bytes and leave no partial implementation or Capability Catalog publication.
- **FR-021**: Implementation publication and Capability Catalog publication MUST occur atomically as one successful operation.
- **FR-022**: Regeneration MUST remove or replace derived rows no longer supported by accepted Reference Implementation evidence and MUST NOT retain orphaned capability rows.
- **FR-023**: Assessment workflows MUST be able to identify the owning RI and realization providers directly from the Capability Catalog.
- **FR-024**: The catalog MUST allow the organization's technology landscape to emerge from accepted implementation knowledge without creating a separate technology inventory.
- **FR-025**: Capability Catalog generation MUST NOT mutate Reference Architectures, ADRs, Objectives, Controls, NFRs, assessment findings, or other source-owner artifacts.
- **FR-026**: Verification MUST confirm generation from implementation evidence, uniqueness, parent integrity, realization completeness, business-outcome semantics, deterministic output, absence of CAP record files, assessment addressability, and atomic publication.

### Key Entities

- **Capability Catalog**: The repository-wide generated index at `implementations/capabilities.md` containing Version, Next ID, and capability rows.
- **Capability Index Entry**: One catalog row identified by `CAP######`, with exactly one `RI######` Parent, a business-readable Title, and one or more Realized By values.
- **Reference Implementation**: The authoritative `RI######` artifact whose accepted evidence gives a capability its meaning and ownership.
- **Realization**: The provider, platform, product, technology, service, process, or mechanism responsible for delivering a capability.
- **Capability Identifier**: A catalog-local `CAP######` value used for navigation and stable row identity, not a standalone artifact identity.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In 100% of successful runs, every catalog row contains exactly one valid `RI######` Parent and at least one non-empty Realized By value.
- **SC-002**: In 100% of successful runs, every CAP identifier is unique within the catalog and no standalone CAP record file is created.
- **SC-003**: In 100% of repeated runs with identical accepted implementation inputs and catalog state, catalog bytes, identifiers, version behavior, and ordering are identical.
- **SC-004**: In 100% of generated catalogs, rows are ordered by Parent, Title, and CAP identifier as specified.
- **SC-005**: In 100% of validation, allocation, or write failures, pre-operation implementation and catalog bytes remain unchanged and no partial publication is observable.
- **SC-006**: In acceptance testing, at least 90% of business stakeholders can distinguish capability titles from implementation component names and locate the owning RI and provider for sampled rows.
- **SC-007**: In 100% of assessment fixtures containing catalog references, assessment can identify the directly associated RI and realization provider without consulting a separate technology inventory.
- **SC-008**: In 100% of regeneration fixtures, no catalog row remains whose Parent or capability evidence is absent from accepted Reference Implementations.

## Assumptions

- Reference Implementation generation and acceptance remain the authoritative source for capability evidence; this feature does not define a new capability authoring workflow.
- `implementations/capabilities.md` is the single repository-wide catalog for the MVP.
- Capability identifiers are catalog-local and do not require individual Markdown records.
- The implementation workflow already has authoritative input resolution, validation, identifier allocation, and atomic publication conventions that this catalog extends.
- Assessment may consume the catalog as repository context, but assessment remains advisory and does not own or mutate capability entries.
- Technology landscape analysis is derived from Realized By values and accepted implementation evidence; a separate technology inventory is out of scope.
- Missing capability evidence is represented by no catalog row rather than by an invented capability or placeholder provider.

## Scope Boundaries

### Included in Version 1

- Generated capability index at `implementations/capabilities.md`.
- CAP###### allocation and uniqueness validation.
- RI parent integrity and one-or-more realization validation.
- Business-outcome title validation.
- Deterministic ordering and regeneration.
- Atomic publication with Reference Implementation output.
- Assessment/provider navigation from the catalog.

### Excluded from Version 1

- Standalone capability records or a capability workflow.
- Capability ownership independent of a Reference Implementation.
- A separate technology inventory.
- Architecture, ADR, governance, assessment, planning, task, code, deployment, or productization mutations.
- Semantic inference that invents capabilities or providers without accepted implementation evidence.
